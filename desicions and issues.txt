ISSUE 1 (FIXED, commit d291651c): dev_workspace.py's ADO routes never checked
project-scoped personal credentials. A project admin can save an Azure DevOps
PAT for just their own project via the Integrations page
(project_integration_credentials table), but every route in dev_workspace.py
resolved credentials via ado_repos.resolve_auth(tenant_id) alone, which only
checks a TENANT-WIDE connector -- it never passed project_id/owner_id to
get_connector_for_session, so the project-scoped override
(config/connectors/base.py::_resolve_credential_override) was never even
attempted, despite that mechanism already existing in the codebase for
exactly this purpose. Root-caused with systematic-debugging: confirmed
resolve_auth(tenant_id) alone returns ("", "") for a real project with a
saved credential, confirmed passing project_id+owner_id resolves it
correctly, then fixed by threading project_id/owner_id through resolve_auth,
_resolve, list_projects, list_repos, list_branches, and resolve_clone_url
(all optional/keyword-only, backward compatible), updating dev_workspace.py's
five route handlers to pass them from the path project_id and
request.state.user_id they already have. One new regression test added
(test_resolve_auth_forwards_project_id_and_owner_id_to_the_connector_factory).

ISSUE 2 (ENVIRONMENT, not code -- worked around, not "fixed"): port 8001 had
a phantom Windows/Hyper-V NAT entry -- netstat/Get-NetTCPConnection showed it
"LISTENING" under a PID that Get-Process/tasklist both confirmed did not
exist, yet it silently answered some real HTTP requests with a bare 500
"Internal Server Error" (no JSON, no application log entry at all -- proven
by reproducing the identical request in-process via FastAPI TestClient, which
returned a correct 200 with real data every time, proving the actual
application code was already correct). This is a known class of issue when
Docker Desktop's Hyper-V networking is involved; the proper fix
(`net stop winnat` / `net start winnat`) needs admin rights not available in
this session. WORKAROUND: moved the backend from port 8001 to port 8002
entirely (backend/.env's AGENTIC_BASE_URL/AGENTIC_WS_URL, frontend/.env.local's
FASTAPI_INTERNAL_URL) and restarted both servers cleanly. Also found and
killed several duplicate backend/frontend process trees that had accumulated
across this session's earlier restarts, going orphaned when the session's
underlying MCP connection recycled mid-conversation (visible from separate
task-notification output-file paths before/after) -- background `&` processes
started without the harness's own run_in_background tracking do not survive
that boundary, even though they keep running as real orphans afterward.
FOLLOW-UP FOR THE USER: if this recurs on a future machine restart, running
`net stop winnat && net start winnat` as Administrator is the real fix; the
port-8002 workaround is durable for this session but not a root-cause fix.

ISSUE 4 (FIXED, commit 3e6d9c8): chat never worked in local auth mode,
platform-wide, not just for Development. Sending a message in the chat
drawer showed the user's own bubble and then nothing -- no response, no
visible error. Root-caused with systematic-debugging: the frontend's own dev
log (not the backend's -- the backend never even saw the request) showed
`[chat-bridge] failed to open WS connection: Error: mintBffToken is not
permitted in local mode.` frontend/lib/bff/ws-ticket.ts::mintWsTicket()
called mintBffToken() directly, which throws BY DESIGN in local mode
(lib/bff/jwt.ts -- a documented, deliberate security guard from an earlier
RBAC audit: a local session's permissions come from a client-writable cookie
and must never be signed into a trusted JWT claim). Every OTHER BFF->FastAPI
call already goes through bearerForRequest() (lib/bff/client.ts, already
tested in __tests__/bff/client.test.ts), which correctly forwards the real
FastAPI-issued login token in local mode instead of minting a new one --
mintWsTicket was simply the one call site never updated to that established,
already-correct pattern.
BLAST RADIUS: mintWsTicket is the single shared ticket-minting function
behind app/api/chat/route.ts (every agent's chat drawer, all 8 agents, not
just Development), app/api/copilot/ws-ticket/route.ts (the Orchestrator
Copilot), and app/api/runs/[id]/stream/route.ts (run SSE streaming) -- this
one bug broke real-time chat and streaming platform-wide in local auth mode.
Never caught before because every prior chat-access test (this session's
Tasks 2-9 included) exercised the backend WS handler directly, bypassing
this Next.js bridge entirely -- this is the first time any of this work was
exercised through the real browser UI.
FIX: one-line change -- mintWsTicket now calls bearerForRequest(session)
instead of mintBffToken(session). Regression test added
(__tests__/bff/ws-ticket.test.ts, 2 tests: local mode forwards the real
token and never mints; enterprise OIDC mode still resolves via the Auth0
token path) mirroring the existing, already-passing bearerForRequest test
suite's exact mocking pattern.

ISSUE 5 (FIXED, commit 30ea0115): after Issue 4's fix got the chat WS
connection genuinely open, the very first real message to a project
configured with an azure/gpt-5-mini model failed every time with
"Agent error: UnsupportedParamsError" -- the log deliberately carries only
the exception type (never str(exc), which routinely echoes credentials back
for auth-related errors), so the real message needed reproducing directly
against the live deployment to see. Confirmed:
`litellm.UnsupportedParamsError: gpt-5 models (including gpt-5-codex) don't
support temperature=0.1. Only temperature=1 is supported.`
Root cause: agents/dev_agent.py::_build_llm() hardcoded temperature=0.1
unconditionally for every model, every provider. gpt-5-family models reject
any temperature other than their own default (1) outright rather than
clamping it -- confirmed by reproducing the identical ChatLiteLLM call twice
against the real azure/gpt-5-mini endpoint: fails with temperature=0.1 set,
succeeds the instant it's omitted.
FIX: _build_llm now skips the temperature kwarg specifically when the model
string contains "gpt-5", leaving the provider's own default in effect.
Every other model keeps the existing low, determinism-favoring 0.1 this
agent wants for code generation. Deliberately NOT litellm's global
`drop_params=True` escape hatch, which would silently swallow any other
unsupported param for every model everywhere -- this is a narrow, verified
exception for the one model family that structurally cannot take the
parameter. Regression tests added (test_dev_agent_build_llm.py): gpt-5 and
gpt-5-codex get no temperature kwarg, other models keep 0.1, the
alias/model cache still dedupes correctly.
FOLLOW-UP NOTED, NOT FIXED: Security/Documentation/Code Review/other agents
likely each have their own equivalent _build_llm-shaped function with the
same hardcoded-temperature pattern (not yet checked/confirmed) -- worth
auditing if any project ever configures a gpt-5-family model for those
agents too. Out of scope for this Development-agent-focused session.

ISSUE 14 (FIXED, commit 3054c5c2): on the very next real request after
Issue 13 deployed, the user hit "Agent error: RateLimitError" and asked
directly whether this was Azure's fault or this codebase's fault --
correctly refused to guess and pulled the real error text from the
backend log instead of speculating.
The proximate cause IS genuinely the provider: the real Azure error is
"AzureException RateLimitError - Your requests to gpt-5-mini for
gpt-5-mini in swedencentral have exceeded rate limit." -- real quota
exhaustion from real traffic (a large share of it this session's own
heavy live-testing today across the chat-overhaul verification work).
But the log also showed something making it meaningfully worse, which IS
a code bug: guarded_completion's own retry loop (shared/services/
model_call_wrapper.py -- 3 attempts, 2s/4s backoff, deliberately NOT a
tenacity wrapper per its own docstring, specifically so retries stay
logged/controlled/cost-checked) was firing at the same time as a SECOND,
completely uncoordinated retry layer: ChatLiteLLM's own built-in
tenacity-based retry-on-RateLimitError, enabled because _build_llm passed
max_retries=2 straight into its constructor across all three agents that
share this pattern (Development, Design/Architecture, Requirements). A
single guarded_completion call could therefore fire up to 3x3=9 real
requests at Azure instead of the intended 3 -- piling more load onto an
endpoint that was already telling every caller to back off, plausibly
extending how long the rate limit stayed hot rather than helping recovery.
FIX: max_retries=0 on ChatLiteLLM's constructor in all three agents --
guarded_completion is now genuinely the only retry mechanism, matching
what its own docstring already claimed it was. Regression test added for
Development's _build_llm (the other two share the identical pattern with
no prior dedicated unit coverage to extend). 53/53 tests pass across the
affected Development-agent suites.
ANSWER TO THE USER'S QUESTION: both, but in different senses -- the rate
limit itself is a real, external, provider-side fact (not something this
code controls), but this code was making the SYMPTOM worse by retrying
harder than intended during the exact condition where backing off matters
most. The fix doesn't raise or bypass Azure's quota (not something a code
change can do) -- it stops this codebase from accidentally amplifying
load against it.
